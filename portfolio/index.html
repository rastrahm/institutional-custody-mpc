// 01 — CONTEXTO

Por qué este proyecto

La custodia institucional no es una EOA: exige consenso M-of-N, validación on-chain de firmas (EIP-712 / ERC-1271), límites operativos y rotación de keys con delay. Este módulo construye ese vault con Foundry y cierra con gas, fuzz/invariantes y matriz SWC.

// 02 — TRES PILARES

Qué entrega el módulo

// PILAR_01

Threshold + EIP-712

CustodyVault ejecuta calls con firmas M-of-N ordenadas sobre typed data; anti-duplicado y replay por nonce.

  • InvalidThresholdSignature
  • Unsorted / Duplicate reject
  • ETH vía .call + CEI
// PILAR_02

ERC-1271 + spending

isValidSignature para dApps; path under-limit con 1 owner y cap diario rolling (1d); quorum bypassea el límite.

  • Magic 0x1626ba7e
  • DailyLimitExceeded
  • Fuzz ventana 1000 runs
// PILAR_03

Guards + Timelock + SWC

Guards pre/post, recovery timelock para owners/threshold, gas snapshot y auditoría SWC-100–136 con 0 vulnerables.

  • GuardRejected · self-call setGuard
  • 69 tests (unit/fuzz/invariant)
  • 0 SWC vulnerables

// 06 — CAMPAÑAS DEFENSIVAS

Custody que debe fallar

Cada campaña es un suite Foundry donde el “ataque” (firmas unsorted, over-spend, guard reject, early timelock) debe revertir. Sin PoCs ofensivos: integridad del vault.

A

Threshold

Unsorted / dup / non-signer / under-M → revert.

B

Replay

Mismas firmas tras nonce++ fallan.

C

Spending

Over daily cap → DailyLimitExceeded; fuzz ventana.

D

Guards

Pre/post reject → GuardRejected; nonce intacto en pre.

E

Timelock

Early / expired / wrong data → Timelock* / Unauthorized.
